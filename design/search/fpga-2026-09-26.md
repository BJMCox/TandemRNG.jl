# FPGA implementation cost: initial assessment

The user selected AMD/Xilinx. This assessment uses UltraScale+ DSP48E2 as the
reference. It contains source analysis and hardware estimates, not synthesis results.
No FPGA part, clock target, or resource budget is fixed yet.

## Tandem hardware

The exact [v2 step](../../src/core.jl) takes 256 state bits and produces 128 output bits.
It uses two independent unsigned 32×32→64 products, one 32-bit constant add,
eleven 32-bit XOR operations, and fixed rotations. Both product halves matter.
The fixed rotations are wire permutations. Setting the multipliers' low bits costs
no general OR circuit. Logic and routing still depend on the implementation.

F uses this same step eight times, with a round-constant XOR and a half swap.
A compact design can share its step unit with seeding. At K32, 40 step evaluations
produce 32 blocks. This costs 2.5 wide products per 128 output bits, including seeding.
These counts follow from [the stream and seeding specification](../../SPEC.md).

One chunk needs 256 state bits. The canonical Julia stream interleaves eight chunks,
so an efficient implementation needs eight contexts: 2,048 state bits. It also needs
the key, counters, control, and pipeline registers. Eight contexts can share one step
unit. They need not replicate the arithmetic eight times. This round-robin schedule
can hide a pipeline latency of at most eight cycles if its memory ports sustain one
context read and write per cycle. Longer latency needs stalls or a different schedule.

## AMD multiplier area

A DSP48E2 has a 27×18 signed multiplier, so a full unsigned 32×32 product spans several
slices. [AMD DSP48E2 reference](https://docs.amd.com/r/en-US/ug1704-spartan-ultrascaleplus-libraries/DSP48E2).

An explicit 16-bit limb decomposition needs four 16×16 products, hence four slices
per wide product and eight for a parallel Tandem step. A three-product Karatsuba
decomposition uses 17×17 unsigned operands for the cross term; those fit with sign
padding. That suggests six slices plus more add/subtract logic for the two products.
**Six to eight DSP slices is a construction estimate, not a measured mapping.**
Vivado can trade DSPs, fabric logic, and pipeline depth. AMD's isolated multiplier
results show these tradeoffs but do not measure Tandem.
[Multiplier resource results](https://download.amd.com/docnav/documents/ip_attachments/mult-gen.html).

A single shared wide multiplier can roughly halve that multiplier budget at a lower
step issue rate. Further serialization can use fewer DSPs. Compare designs at the
same output rate, not just by their minimum possible DSP count.

## Comparators

| Generator | Work per output block | Hardware implication |
| --- | --- | --- |
| Tandem K32 | 2.5 variable wide products per 128 bits, including F | Small shared arithmetic unit, eight contexts for the canonical stream |
| Philox4x32-10 | 20 constant wide products per 128 bits | Same two-multiply round shape, repeated ten times; constant multiplication can simplify |
| Threefry4x32-20 | 20 add/rotate/XOR rounds per 128 bits, plus key injections | No multiplier requirement; area grows with unrolling |
| xoshiro256** | XORs, fixed shifts/rotations, and multiplication by 5 and 9 per 64 bits | Constant products reduce to shift/add networks; likely much smaller without DSPs |

The reference counts come from the authors' implementations:
[Philox](https://raw.githubusercontent.com/DEShawResearch/random123/main/include/Random123/philox.h),
[Threefry](https://raw.githubusercontent.com/DEShawResearch/random123/main/include/Random123/threefry.h),
and [xoshiro256**](https://prng.di.unimi.it/xoshiro256starstar.c).
The area comparisons are inferences from those operations. xoshiro does not supply
Tandem's bounded-cost addressed chunk reconstruction. Philox computes each block
directly from its counter. Report those service differences with area and throughput.

Tandem's eightfold reduction in product count versus Philox does not imply eightfold
smaller area or eightfold higher clock speed. Variable multipliers, feedback latency,
state access, and constant-coefficient optimization all affect the result.

## Throughput model and next measurement

If the shared unit accepts one step each cycle, the K32 average is
`128 × 32 / 40 = 102.4` output bits per cycle. At an achieved 300 MHz, that is
30.72 Gbit/s, or 3.84 GB/s. This is a conditional model, not an Fmax prediction.

The useful experiment is three bit-exact RTL implementations on one selected part:
a two-product Tandem step with eight contexts, an iterative Philox round unit,
and a compact xoshiro256** core. Add Threefry if DSP availability drives the choice.
Sweep pipeline depth and sharing, then compare post-route output rate, LUTs, FFs,
DSPs, memories, and output rate per resource. Include seeding and sustained stream
output. Check SPEC vectors, row order, reseeding boundaries, and backpressure replay.
Measure raw bits first; report floating-point format conversion separately.
